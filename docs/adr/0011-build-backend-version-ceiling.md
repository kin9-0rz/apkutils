# 构建后端封顶到下一个 minor，由 CI 金丝雀门禁防止漂移

ADR-0010 决定「运行时依赖只写下限，不写预防性主版本上限」，但**其结论不延伸到构建后端**。两者的方向相反，理由在 uv 自己的版本策略里——uv 不使用「0.x 下 minor 可自由破坏、1.0 才稳定」的惯例，而是规定 **minor 号本身用于破坏性变更**（`docs.astral.sh/uv/reference/policies/versioning`）。因此对一个已发布的 sdist 而言，未来的 `uv_build` minor 可能直接使其构建失败；而运行时依赖的破坏性变更表现为**运行时**失败，使用者可以自行把依赖钉回旧版本自救，构建后端没有这条退路，产不出来就是产不出来。ADR-0010 的取舍前提是「出问题时谁能自救」，构建后端里这个前提不成立，所以它得到相反的结论。

决策：**`[build-system].requires` 声明上限，封在下一个 minor。**

- 下限为**实际验证过的版本**，而不是迁移残留的旧值。当前写作 `uv_build>=0.12.18,<0.13`。
- 上限形式采用 uv 官方文档的两段式写法（`<0.13`），与我们引用的文档保持一致；PEP 440 下 `<0.13` 与 `<0.13.0` 等价。

**防止再次腐烂的机制：CI 金丝雀门禁。** 光有上限不够——这个 pin 的过期是无声的：`uv build` 只打印 warning 并以 **0** 退出，而 dependabot 的 `uv` 生态 parser 不解析 `[build-system]`（其 `python` 生态 parser 会解析，但本仓库只配置了 `uv` 与 `github-actions`，见 `.github/dependabot.yml`），所以没有任何自动更新覆盖它。为此新增名为 `build-backend` 的 CI job：跑 `uv build`（默认同时构建 wheel 与 sdist），只要输出出现「当前 uv 版本不在声明范围内」或「缺少上限」类 warning 就失败。**必须构建 sdist**：后一类 warning 只在该路径发出，只跑 `uv build --wheel` 会漏掉「上限被删」这一情形。该 job **刻意不钉住 uv 版本**（`setup-uv` 默认装最新），因此上游发布新的 uv minor 时它会变红，逼出一次同步 bump——这是金丝雀信号，不是缺陷。

这里需要正面回应 ADR-0010 的一条 Consequences：「上限的引入需要理由，而非默认。只有**已知或极可能不兼容**时才临时添加，并应尽快移除。」本篇不违反它，而是划定它的边界——那条规则的前提同样是「出问题时谁能自救」：运行时依赖的破坏性变更随时可由使用者钉回旧版，所以永久上限只是负担；构建后端没有这条退路，上限因此是**结构性的、非临时的**，不是为某个已知不兼容打的补丁。

## Considered Options

**运行时与构建后端都不封顶**被拒绝：它按 ADR-0010 的直觉把两条规则统一，却抹掉了上面那条真实差异——构建后端的破坏性变更无法由下游自救，且 sdist 一旦发布就带着这个上限再也改不了。

**折中上限（例如 `<1.0`）**被拒绝：uv 的政策是 minor 即破坏性变更，`<1.0` 等于放行全部破坏性升级，与加上限的初衷自相矛盾；它省下的维护频率，代价是护栏形同虚设。

**交给 Renovate 自动 bump**（其 `pep621` manager 明确支持 `build-system.requires`）被拒绝：收益是「真的会 bump」而非「只是报警」，但代价与本仓库规模不成比例——要么引入一个新 bot，要么给 dependabot 加一个 `pip` 生态条目，而后者会与现有的 `uv` 条目抢同一批 `project.dependencies`，产生重复 PR。uv 每个 minor 的 CHANGELOG 都会主动给出新的上限写法，配合 CI 一道变红，一名维护者完全吃得下。

**只在文档里记一笔、不做门禁**被拒绝：那与「什么都不做」的差别仅在于是否承认它会腐烂，治不了无声漂移。

## Consequences

- 构建后端与运行时依赖从此有**两条方向相反的规则**：前者封顶、后者只写下限。看到 ADR-0010 又看到这个上限的人，应先读本篇再下结论。
- 上限的 bump 是手工的、由一个**会主动变红的 CI check** 推动；本仓库据此**必须保持该 check 为必需检查**，否则金丝雀叫声没人听。
- 该 pin **不影响 wheel 使用者**（wheel 不含 `build-system`），只影响从 sdist 构建的人；本仓库当前只发 wheel，所以这条决策的实际暴露面很小——这也是它没有更早被处理的原因。
- 与 ADR-0010 相同的一点：上限是**契约**，一旦随 sdist 发布便不可再改；因此下限必须准确，本例取的是实际验证过的版本而非猜测。
