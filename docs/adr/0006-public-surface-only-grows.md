# 向后兼容是硬约束：public 成员只增不减

apkutils 已发布到 PyPI（当前 2.0.5），`APK` 的 public 成员被下游直接调用。因此：不删除、不改名、不改签名任何已发布的 public 成员；新能力只通过新增可选参数或新增属性/方法引入；破坏性变更只能进下一个 major 版本。

## Consequences

这条约束重了重构的手——私有 module 的命名与拆分自由度（见 ADR-0001）正是为了让 public 边界不必随之变动。任何「顺手删掉一个没人用的 public 方法」都不成立，必须先确认它从未发布。

## 补充（窗口是会用掉还是会被错过）

同一个 major 窗口在 3.0 与 4.0 上表现完全不同，值得记下来。

**3.0 准点用掉了窗口。** `unzip` 移入 `zip` 子组且不留别名（ADR-0013）的那个 commit `d1d4e9a` 就是 `v3.0.0` tag 指向的 commit——破坏性变更随窗口一起交付，从上一个发布 `v2.1.1` 到 `v3.0.0` 之间没有加垫片，没有多占发布周期，代价为零。这条约束按设计运作的样子就是这一种。

**4.0 是补上一次被错过的窗口。** ADR-0009 把删除期限写死为 3.0，但 3.0 与 3.1.0 都带着那三个 property 发布了。写死期限没有降低代价，只是把它推迟到更晚，并且让它们多占一个发布周期的公开表面（ADR-0009 的「补充（4.0 兑现）」记了这段）。

差别不在这条约束写得好不好，而在窗口有没有被真的用掉——而这取决于写期限的那一刻有没有把它当成**会过期的东西**。「只在 3.0 有效」被当成历史陈述时，它就成了一个会悄悄过期的承诺。补上对照，是为了让下一个人读到「3.0」这个数字时知道它曾经是个真问题，而不只是记录里的一行字。
