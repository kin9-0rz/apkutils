# 依赖声明只写下限，主版本升级由 CI 与人工评审把关

`pyproject.toml` 的运行时依赖长期是「4 个带主版本上限、2 个不带」。这不是决策的结果：2024-10-12 的 `edc2d08`（Poetry 切换到 rye）把 Poetry 的 `^X.Y.Z`（语义等价 `>=X.Y.Z,<下一主版本`）机械转写成 PEP 621 写法，于是 `Pygments`/`beautifulsoup4`/`click`/`pyftype` 四个声明带上了上限；`cryptography` 当时已是裸 `>=39.0.1`，保持原样；`lxml` 当时是 `^4.6.4`（带上限），但在同一提交里为兼容 Python 3.13 被提高并写成不带上限的 `>=5.0.0`。「4 有 2 无」这个形状就是那一次提交的产物，仓库没有任何地方记录过依赖约束的立场。

决策：**运行时依赖只写下限，不写预防性主版本上限。**

- 上限挡不住安全修复：Dependabot 的 security update 在修复版本落在范围外时会自动放宽上限并开 PR，所以它换不到「安全网」。
- 上限随某个版本发布到 PyPI 后**不可再修改**。要让上限放宽，必须改约束并**再发一次版**；而锁了旧版的使用者，其上限永久存在——要么被静默装在有漏洞的版本上，要么 resolver 无解，两种情况下使用者都无法自救。
- 不设上限时，上游的破坏性变更表现为**运行时**失败，使用者可自行把该依赖钉回旧版本自救，维护者也无需为此发版。
- 所以这不是「宽松 vs 严格」的取舍，而是**「出问题时谁能自救」**的取舍。

代价是下限成为唯一的契约，因此它必须准确。`lowest-direct` 的下限验证进入 CI：直接依赖降到各自下限后跑完整测试。当前下限（`Pygments>=2.12.0`、`beautifulsoup4>=4.10.0`、`click>=8.0.3`、`cryptography>=39.0.1`、`lxml>=5.0.0`、`pyftype>=1.2.4`）经该检查验证通过。

## Considered Options

**补齐所有上限**（保留现有 4 个，并给 `cryptography`、`lxml` 补上）被拒绝：它消除的是「不一致」这个表象，而不是代价本身——不可修改性与无法自救的问题原样存在，只是被统一施加到 6 个依赖上。

**维持现状**被拒绝：现有形状是迁移残留而非决策；把它当成约定，等于把一次转写事故固化成先例。

**只加下限验证、不改声明**被拒绝：那会留下一个已被证伪的约束，并要求维护者长期为每次上游大版本发版。

## Consequences

- 上限的引入需要理由，而非默认。只有**已知或极可能不兼容**时才临时添加，并应尽快移除。
- ADR-0006 的硬约束作用于我们自己的 public surface；给依赖加主版本上限是把硬约束施加给**下游**，方向相反。
- 主版本升级的把关从「声明层面拒绝」移到「CI + 人工评审」：移除上限后，Dependabot 的定时版本更新会开始提出主版本升级（此前只有 security update 能穿透上限），评审这些 PR 时不能假设是 patch 级。
- 下限若被证明不准确，应以 `lowest-direct` 的实测结果为依据调整，不得凭猜收紧。
